# FLEET — submission package draft (v0.3, 2026-11-08)

**Nothing in this file is a submission. Nothing was sent anywhere.** It is the
draft the human approves, edits, and sends. The human fills every field marked
PLACEHOLDER; the agent will not type, guess, or fabricate those values, and
will not send any request. When the human is ready, the human or the agent
(on the human's explicit word, with the final JSON printed and approved) sends
ONE request to the submission API.

All rules below come from the live `https://nearhackathon.com/HACKATHON.md`
(fetched 2026-11-08; dates, tracks and API contract re-checked then).

```json
{
  "requestId": "86665ccd-ff1e-4390-9793-fcd18bd86e54",

  "leadName": "<HUMAN: team lead's name, 2-80 characters>",
  "email": "<HUMAN: contact email, max 160 characters>",
  "size": "<HUMAN: one of '1', '2 - 4', '4 - 6', '6 - 8', '8+'>",
  "tracks": ["security"],
  "nearAddress": "<HUMAN: mainnet NEAR account for the prize payout; create it yourself in your NEAR wallet — never invented, never generated by FLEET>",
  "projectUrl": "<HUMAN: https://github.com/<org>/<repo> — the public repository after you make it public>",
  "demoUrl": "<HUMAN: the X post URL you publish>",
  "idea": "Agent fleets on NEAR hand every agent a key and manage it by hand — one compromised key can halt a whole fleet, or drain it silently. FLEET is a key-lifecycle control plane for NEAR agent accounts: scoped FunctionCall operator keys with receiver and method ACLs, a one-transaction freeze stop switch with a public refusal receipt, tag-based bulk revocation, governed single-admin rotation, lost-admin recovery, and a SHA-256 audit chain verifiable on-chain. Native NEAR access keys, not a custody contract — FLEET never holds your keys, and never moves your assets. A 2-of-2 multisig admin mode (Mode B) raises the bar for who can freeze, per account, on-chain. Every claim maps to a VERIFIED CLAIMS.md row backed by testnet evidence.",
  "consent": false
}
```

Notes on the JSON:

- `requestId` is generated once and stored here on purpose: if the network
  response is lost and you retry, reuse the **same** id (the server then
  treats the retry as the same submission). Keep the id with you; do not
  commit it with any email or personal data — this file has none.
- `consent` stays `false` until you, the human, have read the contact notice
  verbatim and answered yes:
  *"I agree that the organizers may use these details to review our submission
  and contact us about this hackathon."*
- `tracks` is exactly `["security"]` — one track, one project.
- `idea` is 734 characters (contract requires 20–2000); the agent may edit
  wording before you send, but never below 20 characters or above 2000.
- `projectName` "FLEET" follows the working name; if the human picks a rename
  (Item 4), both `projectName` and the repository/display copy change
  together in the rename commit.
- Do not add any fields. `website` is a spam trap; non-empty rejects.

## Agent-done vs human-only — the line

The agent may: verify every field's validity (sizes, regexes, track id),
print the final JSON, count characters, check the claims table and
fresh-clone, and remind the human of the rules above. The agent may not:
invent or type name/email/size/payout/demo URL, mark `consent: true`, send
any HTTP request to the submission API, make the repo public, post the demo,
or register/submit anything. **Every action above that sends, publishes or
spends requires the human's explicit confirmation in this session or in the
file they control.**

## After a 201 (what everyone tells the human)

- A 201 means the submission is saved. Print the response (201 + body) for
  the record, tell the human, and append the hash of the request (requestId)
  — not the personal data — to the local working notes only.
- If the human prefers the browser form: https://nearhackathon.com/#apply —
  same fields, same rules.
- Any mistake found later: the human requests changes by hand at
  https://nearhackathon.com/request-changes; the agent helps gather values
  but never sends.
